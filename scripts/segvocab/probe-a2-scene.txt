=== SQL follow-up: are those three "Module | ../scene/Scene" rows one node's id repeated,
    or three distinct nodes that share a label? ===

sqlite> SELECT id FROM nodes_fts WHERE nodes_fts MATCH '"scene"' ORDER BY rank LIMIT 3;
packages/excalidraw/frame.ts#import:./scene/Scene
packages/excalidraw/element/mutateElement.ts#import:../scene/Scene
packages/excalidraw/element/dragElements.ts#import:../scene/Scene

Three distinct ids -- three distinct import-reference ("Module") nodes, one per import
site, that legitimately share the label "../scene/Scene" because excalidraw imports that
module from many files. This is NOT the nodes_fts duplicate-row defect: it is ordinary
label collision among genuinely different nodes, which `type`+`label` alone cannot tell
apart from a true duplicate id, and which the original probe's output (type+label only)
could not have distinguished either -- so "the same node three times" was not something
that probe's output actually established; it was a reasonable-looking but unverified
reading of output that is equally consistent with this more mundane explanation.

Yes: the defect is real and present in this same cold index (219 excess rows; one id --
a CHANGELOG.md section -- occupies 33 nodes_fts rows by itself). It just is not what the
"scene" probe specifically demonstrated. Whether the "scene"-style label-collision
mechanism (many distinct nodes sharing a label) or the id-level duplicate-row mechanism
(one node's id repeated) contributes more to A2's gain over A0c is not established by
either probe; this run still has no data on the magnitude of either, which is why §1's
wording is "partly attributable, magnitude unquantified" rather than "traces
substantially."
