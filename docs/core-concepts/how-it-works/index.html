How It Works

ContextGraph is a pipeline: it discovers files, routes them to extractors, parses source to an AST, resolves references and entities, builds a graph, and writes everything to SQLite in batches. Here's each stage in detail.

1. File discovery

FileDiscovery walks the project directory using the include/exclude glob patterns from your config. Each matching file becomes an Artifact with a path, type, size, and SHA-256 checksum.

On re-indexing, ChecksumTracker compares the current checksum against what's stored. If unchanged, the file is skipped — this makes incremental indexing fast even on large projects.

2. Artifact type detection

ArtifactTypeDetector maps file extensions to NodeType. A .kt file becomes CodeFile, a .sql file becomes DatabaseSchema, a .pdf becomes PDF, and so on. The type determines which extractors run.

3. Parsing and extraction

Source files go to TreeSitterExtractor, which parses them to a tree-sitter AST and walks it for declarations. Grammars ship for Kotlin, Java, TypeScript, TSX, JavaScript, Python, Swift and Objective-C.

Declarations get scope-correct identity rather than a bare name: DeclarationSiteId and Fqn in modules:tree-sitter qualify a symbol by where it is declared, so a close() on one type and a close() on another never collapse into one node. This is the difference between a call graph and a list of coincidences.

IngestPipeline runs extraction with Kotlin coroutines. Each file is processed concurrently on Dispatchers.IO — multiple extractors can run in parallel across many files. Results flow through a Channel to a single consumer that writes to SQLite, avoiding lock contention.

A file with syntax errors is not discarded: tree-sitter recovers, extraction proceeds over what parsed, and the run reports a parse warning.

Each extractor implements ResourceExtractor:

ResourceExtractor.kt
interface ResourceExtractor {
    val id: String
    val supportedTypes: Set<NodeType>
    suspend fun extract(artifact: Artifact, context: ExtractionContext): ExtractionResult
}

An ExtractionResult contains a list of GraphNodes, a list of GraphEdges, and back-references to the source Artifact.

4. Reference and entity resolution

A call site in one file usually names something declared in another, so it cannot be resolved while that first file is being parsed. Unresolved references are recorded and settled after extraction by ReferenceResolver, which walks ResolutionLadder — a sequence of increasingly permissive strategies, from exact qualified match down to name-only matching.

Every edge records which rung resolved it and with what confidence. That is deliberate: an agent reading the graph can tell an exactly-resolved call from a plausible guess, instead of being handed both as though they were the same fact.

EntityResolver then deduplicates nodes across files. If a Class named UserService appears as both a definition in a .kt file and a reference in a Markdown doc, they resolve to the same node with provenance from both sources.

5. Storage

All data is written to SQLite via SqliteStorageAdapter using Jetbrains Exposed as the DSL. The database schema is managed by Flyway migrations.

Writes go through a batch seam on StorageAdapter — writeArtifactBatch, upsertNodes, upsertEdges — so a whole artifact's nodes and edges land on one connection inside one transaction. This is not a micro-optimisation: ContextGraph previously opened and closed a separate SQLite connection per row, and fixing it took a 234k-node Java repository from 142m 55.6s to 8m 16.4s while producing a byte-identical graph.

The key tables:

  • artifacts — one row per indexed file
  • nodes — entities extracted from files, with FTS5 index on label for full-text search
  • edges — typed, weighted relationships between nodes
  • provenance — file + line numbers tracing each node back to its source
  • name_segment_vocab — a lookup from an identifier's sub-words back to the names containing them, populated at index time. Its rows are proposals: every candidate is re-verified against nodes before it is returned, and candidates are appended after the full-text hits rather than interleaved, so a segment match can add recall at the tail but never demote a real hit

Query layer

The QueryEngine sits on top of StorageAdapter and provides higher-level operations: BFS neighborhood expansion (via JGraphT), shortest-path finding, reverse-dependency (impact) analysis, and context bundle assembly for AI agents.

Ranking is a function of the query, not of the graph alone. QueryRelevance scores each candidate against the words actually asked about — including the sub-words of compound identifiers, so a search for "auth" reaches refreshAuthToken — and ContextBundler sorts on that relevance rather than on graph centrality times confidence. Sorting without reference to the query was the single defect behind ContextGraph placing last on every retrieval metric; fixing it moved it to first.

ExploreEngine composes the whole layer into one call: match modules, rank symbols against the question, attach verbatim source until a token budget is spent, mark the remainder elided, and return the resolved edges and blast radius alongside. That is what contextgraph.explore serves over MCP.
